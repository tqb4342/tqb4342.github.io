这几个并行方式，本质上是在回答同一个问题：

❝一个大模型太大、请求太多、计算太慢时，如何把模型和请求拆到多张 GPU 上？

可以先用一句话理解：

并行方式 拆的是什么 直观类比 主要目标
DP 数据并行 拆请求 / batch 多个完整厨师各做一桌菜 提高并发吞吐
TP 张量并行 拆矩阵计算 几个人一起切同一块大肉 让单层计算放得下、算得快
PP 流水线并行 拆模型层 工厂流水线，每人负责几道工序 让超深模型分层放到多卡
EP 专家并行 拆 MoE 专家 不同专家坐在不同办公室 支撑超大 MoE 模型

1. DP：Data Parallel，数据并行

1.1 直观理解

DP 的核心思想是：每组 GPU 上都有一份完整模型，请求被分发到不同副本上处理。

例如有 4 张 GPU，每张 GPU 都能完整放下模型，那么可以这样：

代码语言：javascript

AI代码解释

用户请求队列
    │
    ├── 请求 A ──> GPU0：完整模型副本
    ├── 请求 B ──> GPU1：完整模型副本
    ├── 请求 C ──> GPU2：完整模型副本
    └── 请求 D ──> GPU3：完整模型副本

这就像开了 4 个独立窗口，每个窗口都能完整服务用户。

1.2 DP 在训练和推理中的区别

很多人第一次接触 DP 是在训练中。

训练时：

代码语言：javascript

AI代码解释

不同 GPU 处理不同 batch
      ↓
各自计算梯度
      ↓
AllReduce 同步梯度
      ↓
更新相同模型参数

但是在推理阶段，一般没有反向传播，也没有梯度同步，所以 DP 更简单：

代码语言：javascript

AI代码解释

请求分发到不同模型副本
      ↓
各自独立推理
      ↓
返回结果

因此，推理中的 DP 更像是：

❝多开几个模型服务实例，提高并发处理能力。

1.3 DP 的结构图

代码语言：javascript

AI代码解释

              Load Balancer / Scheduler
                      │
     ┌────────────────┼────────────────┐
     │                │                │
DP Replica 0     DP Replica 1     DP Replica 2
     │                │                │
完整模型副本      完整模型副本      完整模型副本
     │                │                │
 GPU Group 0      GPU Group 1      GPU Group 2

注意，这里的一个 DP Replica 不一定只是一张 GPU。

比如大模型太大，需要 TP=8 才能放下，那么一个 DP 副本可能是：

代码语言：javascript

AI代码解释

DP Replica 0 = 8 张 GPU 做 TP
DP Replica 1 = 8 张 GPU 做 TP
DP Replica 2 = 8 张 GPU 做 TP

也就是：

代码语言：javascript

AI代码解释

DP = 3
TP = 8
总 GPU 数 = 3 × 8 = 24

1.4 DP 的优点

DP 最大的优点是简单、稳定、吞吐扩展好。

当单个模型副本已经可以正常运行时，增加 DP 副本通常可以接近线性提升并发能力。

例如：

代码语言：javascript

AI代码解释

1 个副本：每秒处理 100 tokens
2 个副本：理论上接近 200 tokens
4 个副本：理论上接近 400 tokens

当然，真实场景还会受调度、显存、CPU、网络、KV Cache、请求长度差异影响。

1.5 DP 的缺点

DP 的主要问题是：

❝每个副本都要保存一份模型权重，显存开销大。

如果模型本身已经需要 8 张 GPU 才能放下，那么做 DP 就需要更多 GPU。

例如：

代码语言：javascript

AI代码解释

一个模型副本需要 TP=8
如果 DP=4
总共需要 8 × 4 = 32 张 GPU

所以 DP 适合：

代码语言：javascript

AI代码解释

模型已经能在一个 GPU 组内放下
并且你想提高并发吞吐

不适合：

代码语言：javascript

AI代码解释

模型太大，连一个副本都放不下

这种情况要先考虑 TP、PP、EP。

2. TP：Tensor Parallel，张量并行

2.1 直观理解

TP 是把模型中的大矩阵切开，让多张 GPU 一起完成同一层的计算。

Transformer 里面最重的计算主要是矩阵乘法，例如：

代码语言：javascript

AI代码解释

Y = XW

其中：

代码语言：javascript

AI代码解释

X：输入激活
W：模型权重矩阵
Y：输出

如果 W 太大，一张 GPU 放不下，或者计算太慢，就可以把 W 切开。

2.2 TP 的基本图示

假设一个线性层权重矩阵 W 被切成 4 份：

代码语言：javascript

AI代码解释

原始权重矩阵 W
┌──────────────────────────────┐
│                              │
│              W               │
│                              │
└──────────────────────────────┘

切成 4 份：

┌───────┬───────┬───────┬───────┐
│ W_0   │ W_1   │ W_2   │ W_3   │
└───────┴───────┴───────┴───────┘
   │       │       │       │
  GPU0    GPU1    GPU2    GPU3

每张 GPU 只保存一部分权重，并计算一部分结果。

2.3 TP 的计算流程

以列切分为例：

代码语言：javascript

AI代码解释

输入 X
 │
 ├── GPU0: X × W0 → Y0
 ├── GPU1: X × W1 → Y1
 ├── GPU2: X × W2 → Y2
 └── GPU3: X × W3 → Y3
             │
             ↓
       拼接 / 通信
             ↓
        完整输出 Y

也就是：

代码语言：javascript

AI代码解释

Y = concat(Y0, Y1, Y2, Y3)

在一些层里面还需要做 AllReduce：

代码语言：javascript

AI代码解释

GPU0 局部结果
GPU1 局部结果
GPU2 局部结果
GPU3 局部结果
      │
      ↓
  AllReduce 汇总
      │
      ↓
  每张 GPU 得到完整或所需结果

2.4 TP 为什么常用于大模型推理？

因为 Dense Transformer 模型的很多层都很大，例如：

代码语言：javascript

AI代码解释

Attention 的 Q/K/V/O 投影
MLP 的 up_proj、gate_proj、down_proj

这些矩阵可能非常巨大。

TP 可以解决两个问题：

代码语言：javascript

AI代码解释

1. 单卡显存放不下完整模型
2. 单卡算力不够，需要多卡一起算一层

2.5 TP 的优点

TP 的优点是：

代码语言：javascript

AI代码解释

1. 可以把单层权重拆到多张 GPU 上
2. 适合 Dense 大模型
3. 对单请求延迟也可能有帮助
4. 是 vLLM、TensorRT-LLM、Megatron-LM 等框架常用方式

比如一个 70B 或 100B 级别模型，可能需要：

代码语言：javascript

AI代码解释

TP=4
TP=8

才能比较舒服地跑起来。

2.6 TP 的缺点

TP 的缺点主要是通信频繁。

因为每一层内部都可能需要 GPU 之间通信：

代码语言：javascript

AI代码解释

Attention 层通信
MLP 层通信
Residual 相关通信
Logits 相关通信

所以 TP 对硬件互联要求较高。

理想情况：

代码语言：javascript

AI代码解释

同一台机器内 NVLink / NVSwitch

可以比较高效。

如果跨机器做 TP：

代码语言：javascript

AI代码解释

机器 A 的 GPU 需要频繁和机器 B 的 GPU 通信

可能通信开销很大，效率下降明显。

所以经验上：

代码语言：javascript

AI代码解释

TP 优先放在单机内部
跨机器慎用 TP

3. PP：Pipeline Parallel，流水线并行

3.1 直观理解

PP 是把模型按层切开，不同 GPU 负责不同层。

比如一个 Transformer 有 80 层，可以这样切：

代码语言：javascript

AI代码解释

GPU0：第 1 ~ 20 层
GPU1：第 21 ~ 40 层
GPU2：第 41 ~ 60 层
GPU3：第 61 ~ 80 层

请求从第一段流向最后一段。

3.2 PP 的结构图

代码语言：javascript

AI代码解释

输入 Token
   │
   ▼
┌──────────────┐
│ GPU0         │
│ Layer 1-20   │
└──────┬───────┘
       │ 激活传递
       ▼
┌──────────────┐
│ GPU1         │
│ Layer 21-40  │
└──────┬───────┘
       │ 激活传递
       ▼
┌──────────────┐
│ GPU2         │
│ Layer 41-60  │
└──────┬───────┘
       │ 激活传递
       ▼
┌──────────────┐
│ GPU3         │
│ Layer 61-80  │
└──────┬───────┘
       │
       ▼
输出 Token

这就像工厂流水线：

代码语言：javascript

AI代码解释

工人 1 负责切菜
工人 2 负责炒菜
工人 3 负责装盘
工人 4 负责上菜

每个人只负责一部分工序。

3.3 PP 的关键问题：流水线气泡

如果只有一个请求，它必须依次经过 GPU0、GPU1、GPU2、GPU3：

代码语言：javascript

AI代码解释

时间 1：GPU0 工作，GPU1/GPU2/GPU3 空闲
时间 2：GPU1 工作，GPU0/GPU2/GPU3 空闲
时间 3：GPU2 工作，GPU0/GPU1/GPU3 空闲
时间 4：GPU3 工作，GPU0/GPU1/GPU2 空闲

这会造成大量空闲，叫做：

❝Pipeline Bubble，流水线气泡。

图示：

代码语言：javascript

AI代码解释

时间 →      T1      T2      T3      T4
GPU0       工作     空闲    空闲    空闲
GPU1       空闲     工作    空闲    空闲
GPU2       空闲     空闲    工作    空闲
GPU3       空闲     空闲    空闲    工作

为了提高利用率，需要多个 micro-batch 或多个请求同时进入流水线：

代码语言：javascript

AI代码解释

时间 →      T1      T2      T3      T4      T5      T6
GPU0       A       B       C       D       ...
GPU1       空闲    A       B       C       D
GPU2       空闲    空闲    A       B       C
GPU3       空闲    空闲    空闲    A       B

这样 GPU 就能更连续地工作。

3.4 PP 的优点

PP 的优点是：

代码语言：javascript

AI代码解释

1. 可以把很多层拆到不同 GPU
2. 适合模型深度很大、层数很多的模型
3. 跨机器时比 TP 更容易一些，因为层间只传激活
4. 可以和 TP 组合，形成 TP + PP

例如：

代码语言：javascript

AI代码解释

模型总共 80 层
PP=4
每个 stage 20 层
每个 stage 内部再 TP=8
总 GPU = PP × TP = 4 × 8 = 32

结构如下：

代码语言：javascript

AI代码解释

             Pipeline Stage 0       Pipeline Stage 1       Pipeline Stage 2       Pipeline Stage 3
输入 ───>   Layer 1-20       ───>   Layer 21-40      ───>   Layer 41-60      ───>   Layer 61-80 ───> 输出
              TP=8                  TP=8                  TP=8                  TP=8

3.5 PP 的缺点

PP 的主要缺点：

代码语言：javascript

AI代码解释

1. 单请求延迟可能变高
2. 有流水线气泡
3. 调度复杂
4. 不同 stage 负载不均会拖慢整体

比如某些层更重，某些层更轻，如果切分不均匀，就会出现：

代码语言：javascript

AI代码解释

GPU0 很忙
GPU1 很闲
GPU2 很忙
GPU3 很闲

这会降低整体效率。

4. EP：Expert Parallel，专家并行

4.1 直观理解

EP 主要用于 MoE 模型。

MoE 全称是：

代码语言：javascript

AI代码解释

Mixture of Experts
混合专家模型

MoE 模型里面有很多专家网络，但每个 token 通常只激活其中少数几个专家。

例如：

代码语言：javascript

AI代码解释

总共有 64 个专家
每个 token 只选择 Top-2 个专家

这意味着：

代码语言：javascript

AI代码解释

模型参数很大
但每次实际计算只用一小部分

4.2 MoE 层结构

普通 Dense MLP 是这样：

代码语言：javascript

AI代码解释

输入 Token
   │
   ▼
一个巨大的 MLP
   │
   ▼
输出

MoE MLP 是这样：

代码语言：javascript

AI代码解释

输入 Token
   │
   ▼
Router / Gate
   │
   ├── Expert 0
   ├── Expert 1
   ├── Expert 2
   ├── Expert 3
   ├── ...
   └── Expert N
   │
   ▼
加权合并输出

Router 会判断：

代码语言：javascript

AI代码解释

这个 token 应该交给哪些专家处理？

4.3 EP 的图示

假设有 8 个专家，分布在 4 张 GPU 上：

代码语言：javascript

AI代码解释

GPU0: Expert 0, Expert 1
GPU1: Expert 2, Expert 3
GPU2: Expert 4, Expert 5
GPU3: Expert 6, Expert 7

图示：

代码语言：javascript

AI代码解释

             MoE Router
                 │
    ┌────────────┼────────────┐
    │            │            │
  Token A      Token B      Token C
    │            │            │
    ▼            ▼            ▼
Expert 1     Expert 4     Expert 7
 GPU0         GPU2         GPU3

每个 token 被路由到不同专家，因此需要 token 在 GPU 之间流动。

4.4 EP 的计算流程

典型 MoE 推理流程如下：

代码语言：javascript

AI代码解释

输入 Token
   │
   ▼
Router 计算每个 token 应该去哪个专家
   │
   ▼
All-to-All：把 token 发送到对应专家所在 GPU
   │
   ▼
各 GPU 上的专家计算
   │
   ▼
All-to-All：把专家输出送回原位置
   │
   ▼
合并输出

更形象一点：

代码语言：javascript

AI代码解释

Token 分发前：

GPU0: token a, token b
GPU1: token c, token d
GPU2: token e, token f
GPU3: token g, token h

Router 判断后：

token a → GPU2 的 Expert 5
token b → GPU1 的 Expert 3
token c → GPU3 的 Expert 7
token d → GPU0 的 Expert 1
...

经过 All-to-All 重新分发后，各专家开始计算。

4.5 EP 的优点

EP 的核心价值是：

❝把大量专家参数分布在多张 GPU 上，同时每个 token 只激活少量专家。

优点：

代码语言：javascript

AI代码解释

1. 支持超大 MoE 模型
2. 专家权重不用每张 GPU 都保存
3. 激活参数少，计算量相对可控
4. 对 DeepSeek-V3 / DeepSeek-V4 / Mixtral / Qwen-MoE 这类模型很重要

比如一个 MoE 模型总参数很大，但每个 token 只用一部分专家：

代码语言：javascript

AI代码解释

总参数：数百 B
激活参数：几十 B

EP 就是为了高效管理这些专家。

4.6 EP 的缺点

EP 的主要问题是通信和负载均衡。

问题 1：All-to-All 通信开销大

EP 需要频繁把 token 发送到专家所在 GPU：

代码语言：javascript

AI代码解释

GPU0 发 token 给 GPU1/GPU2/GPU3
GPU1 发 token 给 GPU0/GPU2/GPU3
GPU2 发 token 给 GPU0/GPU1/GPU3
GPU3 发 token 给 GPU0/GPU1/GPU2

这种通信叫：

代码语言：javascript

AI代码解释

All-to-All

它比普通 AllReduce 更复杂，对网络要求高。

问题 2：专家负载不均衡

如果 Router 总是喜欢某几个专家，就会出现：

代码语言：javascript

AI代码解释

Expert 3 非常忙
Expert 7 非常忙
Expert 1 几乎没活
Expert 5 几乎没活

这会导致：

代码语言：javascript

AI代码解释

部分 GPU 很忙
部分 GPU 空闲
整体速度被最忙的专家拖慢

所以 MoE 推理里经常会考虑：

代码语言：javascript

AI代码解释

expert load balancing
专家负载均衡

5. 四种并行方式的核心区别

可以用这张总图理解：

代码语言：javascript

AI代码解释

                   大模型多 GPU 推理并行
                           │
       ┌───────────────────┼───────────────────┐
       │                   │                   │
    拆请求               拆模型              拆专家
       │                   │                   │
       ▼                   ▼                   ▼
  DP 数据并行        TP / PP 模型并行        EP 专家并行
       │              │          │             │
       │              │          │             │
多个完整副本      拆每一层矩阵   拆模型层     拆 MoE 专家
       │              │          │             │
提高并发吞吐      降低单层压力   支撑深层模型  支撑超大 MoE

6. 用一个厨房类比整体理解

假设大模型是一家超级餐厅。

DP 数据并行

代码语言：javascript

AI代码解释

开 4 家一模一样的餐厅

9.2 TP

TP 可能降低单请求延迟，因为一层计算被多卡分担。

但是 TP 通信频繁，如果通信慢，反而可能变慢。

代码语言：javascript

AI代码解释

TP 好不好，取决于：
计算节省 > 通信开销

9.3 PP

PP 更偏向解决模型放置问题和吞吐问题。

如果请求少，PP 容易有流水线气泡，单请求延迟可能变差。

代码语言：javascript

AI代码解释

9.4 EP

EP 对 MoE 模型非常关键。

如果专家分布合理，EP 可以显著降低单卡专家权重压力。

但如果 All-to-All 很慢，或者专家负载不均衡，速度会下降。

13. 几个容易混淆的问题

13.1 DP 是不是效率最高？

不一定。

DP 的优势是：

但是前提是：

代码语言：javascript

AI代码解释

14. 和 KV Cache 的关系

大模型推理时，KV Cache 非常关键。

DP 与 KV Cache

每个 DP 副本有自己的 KV Cache：

代码语言：javascript

AI代码解释

Replica 0 保存自己请求的 KV Cache
Replica 1 保存自己请求的 KV Cache
Replica 2 保存自己请求的 KV Cache

不同副本之间通常不共享。

优点是简单，缺点是缓存不能跨副本复用，除非系统做了额外的粘性调度或分布式缓存。

TP 与 KV Cache

TP 下，一个请求会跨多个 GPU 共同计算。

KV Cache 通常也会按照 attention head 或张量维度分布在 TP 组内。

代码语言：javascript

AI代码解释

一个请求的 KV Cache
   ├── 一部分在 GPU0
   ├── 一部分在 GPU1
   ├── 一部分在 GPU2
   └── 一部分在 GPU3

所以 TP 组内 GPU 是强绑定的。

PP 与 KV Cache

PP 下，不同 GPU 保存不同层的 KV Cache。

代码语言：javascript

AI代码解释

GPU0：Layer 1-20 的 KV Cache
GPU1：Layer 21-40 的 KV Cache
GPU2：Layer 41-60 的 KV Cache
GPU3：Layer 61-80 的 KV Cache

请求必须按相同的 pipeline 路径走完整个模型。

EP 与 KV Cache

EP 主要作用在 MoE 专家层。

KV Cache 主要来自 Attention 层，因此 EP 本身不是直接切 KV Cache 的主要方式。

不过 MoE 层的 token 分发会影响整体调度、显存和通信效率。
